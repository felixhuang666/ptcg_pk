# RPG Quest System Design

## 1. Overview
The RPG mode utilizes "Quests" as top-level containers for multi-scene gameplay experiences. A Quest groups together multiple `Scenes` and determines the initial entry point for a player when they begin or resume that quest.

## 2. Architecture

### Table Schema (`game_quest`)
```sql
create table public.game_quest (
  id integer generated by default as identity not null,
  created_at timestamp with time zone not null default now(),
  name text not null,
  scene_list jsonb null,
  default_scene_id integer null,
  constraint game_quest_pkey primary key (id)
) TABLESPACE pg_default;
```

### 2.1 scene_list
The `scene_list` is a JSONB array that stores the IDs of scenes associated with the quest. Note that it stores integer IDs, not full scene objects or names. The frontend is responsible for fetching a global scene catalog to resolve these IDs to human-readable names in the UI.

```json
{
  "scene_list": [
    1,
    2,
    5
  ]
}
```

### 2.2 default_scene_id
The `default_scene_id` specifies which scene acts as the starting or default entry point for the quest. When a player selects a quest in the `RpgMode` without a previously saved location for that quest, they will be spawned in the scene matching `default_scene_id`.

## 3. Data Persistence
Quest data relies on a multi-tiered persistence strategy:
- **Supabase Database**: The primary source of truth, interacted with via standard REST CRUD endpoints.
- **Local File Storage**: Quests can be saved locally as JSON files (e.g., `dist/assets/game_quest/{id}.json` or `public/assets/game_quest/{id}.json`) via the `/api/save_local` endpoint.
- **In-Memory Cache**: The backend (`backend/main.py`) maintains an `in_memory_quests` cache that must be kept synchronized when quests are created, updated, saved locally, or loaded from disk.

## 4. Player State Synchronization
When a player is active in a quest, their current location is continuously tracked. The `/api/user/location` endpoint updates the `quest_id`, `scene_id`, and exact positional coordinates in the `game_player_data` table, ensuring their progress is restored upon reconnection.
