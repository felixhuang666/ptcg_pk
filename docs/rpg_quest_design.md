# RPG Quest Design Document

## 1. Overview
The Quest system serves as a top-level macro container for RPG gameplay within "Monster Battle". A Quest groups multiple related RPG Scenes together, defining a cohesive gameplay experience or narrative arc. Players select a Quest to enter, and their progress/location within that Quest is tracked.

## 2. Quest Architecture

### 2.1 Quest Structure
A Quest is primarily defined by:
- **`id`**: Unique identifier (integer for DB, string for local assets).
- **`name`**: The display name of the Quest.
- **`scene_list`**: A JSON array of Scene IDs that belong to this Quest. This defines the boundaries of the Quest's world.
- **`quest_entities`**: Additional metadata, crucially including `default_scene_id`, which dictates where a player spawns when entering the Quest for the first time.

### 2.2 Table Schema
When saved to the database (Supabase), Quests use the following schema:
```sql
create table public.game_quest (
  id integer generated by default as identity not null,
  created_at timestamp with time zone not null default now(),
  name text not null,
  scene_list jsonb null,
  quest_entities jsonb null,
  constraint game_quest_pkey primary key (id)
) TABLESPACE pg_default;
```

## 3. Data Persistence
Quests can be persisted in three locations, providing fallback layers:
1. **Supabase Database**: The primary source of truth for dynamic/online Quests.
2. **In-Memory Cache (`in_memory_quests`)**: A runtime cache in `backend/main.py` used to store dynamically created Quests during a session without requiring a DB roundtrip.
3. **Local Assets**: JSON files stored in `dist/assets/game_quest/` and `public/assets/game_quest/` (e.g., `default_quest.json`). These act as fallbacks if the database is unavailable or for offline testing.

## 4. Components & Workflow

### 4.1 Quest Editor (`src/components/QuestEditor.tsx`)
A dedicated UI component allowing designers to:
- Create new Quests or edit existing ones.
- Add or remove Scenes (`scene_list`) from the Quest.
- Set the default entry point (`default_scene_id`) for the Quest.
- Save the Quest to the database or directly to Local File Assets via `/api/save_local`.

### 4.2 Quest Selection & RPG Mode
When entering RPG Mode (`RpgMode.tsx`):
- A dropdown allows players to select an active Quest from the available list (`/api/quests`).
- Once a Quest is selected, the Map/Scene dropdown dynamically filters to only show Scenes associated with the active Quest's `scene_list`.
- If a player's last Quest ID is missing or invalid, the system automatically loads a default Quest (e.g., `default_quest.json`) to prevent empty states.

## 5. Player Progress Restoration
To maintain continuity, a player's active Quest is tracked persistently:
- A `quest_id` column exists in the `game_player_data` table.
- When a player moves or changes Quests, the `/api/user/location` endpoint is hit, saving the current `quest_id` alongside `map_id` (scene), `pos_x`, and `pos_y`.
- Upon re-entering RPG Mode, the frontend fetches this location data, automatically selecting the last active `quest_id` and restoring the player to their previous state.

## 6. API Reference

### REST Endpoints
- `GET /api/quests`: Retrieves a list of all available Quests, merging results from Supabase, Memory, and Local Assets.
- `GET /api/quest/{id}`: Retrieves full details of a specific Quest.
- `POST /api/quest`: Creates a new Quest in the database and updates the in-memory cache.
- `PUT /api/quest/{quest_id}`: Updates an existing Quest in the database and in-memory cache.
- `DELETE /api/quest/{id}`: Removes a Quest from the database, in-memory cache, and local file system.
- `POST /api/save_local`: Saves Quest data to local file assets (`.json`) and updates the in-memory cache to reflect the changes immediately.
