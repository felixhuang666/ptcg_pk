# RPG Quest Design

## 1. Overview
In the RPG mode, a "Quest" serves as a top-level container for multi-scene gameplay. It defines a high-level goal and orchestrates the transition between multiple game scenes. When a player selects a quest, they are placed into the quest's designated entry point.

## 2. Quest Structure

### Table Schema
```sql
create table public.game_quest (
  id integer generated by default as identity not null,
  created_at timestamp with time zone not null default now(),
  name text not null,
  scene_list jsonb null,
  default_scene_id text null,
  constraint game_quest_pkey primary key (id)
) TABLESPACE pg_default;
```

### 2.1 scene_list
The `scene_list` property contains an array of scene IDs that belong to the quest. The frontend fetches a global scene catalog to resolve these IDs into displayable scene names.

### 2.2 default_scene_id
The `default_scene_id` acts as the entry point for the player when they first begin the quest or when their state is reset.

## 3. State Persistence
The player's active quest in RPG Mode is maintained across sessions.
The `/api/user/location` endpoint is responsible for tracking this state. It updates the `quest_id` column in the `game_player_data` table alongside the player's current scene and position coordinates.

## 4. Backend API Endpoints

The Quest System uses the following REST API endpoints:

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/quests` | List all quests |
| GET | `/api/quest/{quest_id}` | Get quest by ID |
| POST | `/api/quest` | Create new quest |
| PUT | `/api/quest/{quest_id}` | Update existing quest |
| DELETE | `/api/quest/{quest_id}` | Delete quest |

### 4.1 Data Synchronization
Quest data persistence employs a multi-layered approach:
1. **Supabase database**: The primary storage when connected.
2. **Local files**: Fallback assets stored as `.json` files.
3. **In-memory cache**: An active runtime cache (`in_memory_quests` in `backend/main.py`).

These layers must be kept synchronized when quests are modified or saved locally via the `/api/save_local` endpoint.
